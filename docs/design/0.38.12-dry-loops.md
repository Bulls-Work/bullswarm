# 0.38.12 design: loops that stop when a review is dry, and area reviewers

Status: implemented 2026-10-14 (see "Implementation notes" at the end). Written 2026-10-14 against branch
`v0.38.12/ultracode-lessons`, after reading `src/workflow/program-v3.js`,
`gates-loops.js`, `control-nodes.js`, `step-prompts.js`, `answers.js`,
`earlier-work.js`, `v2-runtime.js` (the kernel loop and `runAction`),
`v2-revision.js`, `revision-v3.js`, `v2-state.js`, `v2-outcome.js`,
`v3-display.js`, `watch-cli.js`, `contract-v3.js`, `action-validator.js`
(advisories), the skill (`skill/SKILL.md`, `references/program.md`,
`references/patterns.md`) and `tests/workflow-gates-loops.test.js`,
`tests/workflow-v3-docs.test.js`.

Words used here:

- **finding**: one problem a review reports, as an object in its answer.
- **dry round**: a review round that reports no new in-scope finding.
- **area**: one angle a review looks from ("grammar and parsing").
- **area reviewer**: one copy of a review step that looks from one area.
- **fix-worthy**: a finding that is in scope and either new or reported again
  as still open. Only fix-worthy findings make a fixer run.

## 1. Verdict

1. **Dry stop** is a third condition form, used only as a loop's `until`:
   `{"step": "review", "dry": 1}`. The loop ends after `dry` rounds in a row
   (default and recommended 1, at most 3) in which the review reported no
   fix-worthy finding, and, with areas, every area was reviewed since the last
   fix-worthy finding. The existing `field` and `evidence` forms do not change.
2. The review's answer must hold `findings: [{title, inScope, stillOpen?, …}]`.
   Bullswarm keeps the loop's **known findings** (titles) on the loop's record,
   puts them in every later review prompt as "already known, do not report
   again", and drops exact repeats in code (title compared after trimming,
   lower-casing and collapsing spaces).
3. **No wasted fix pass.** In a dry loop every step other than the review
   runs in a round only when there is something to fix. A step after the
   review (the recommended `[review, fix]` order) is skipped when that
   round's review found nothing fix-worthy; a step before the review (the old
   `[fix, review]` order) is skipped when the previous round's review found
   nothing fix-worthy (round 1 always runs it). The dry check is made right
   after the review finishes, so a dry round never starts a fixer and never
   starts another round. A skipped step is recorded as such (a new fact on
   the step, `skipped`), never as proven.
4. **Area reviewers are real steps.** A review step with `areas` is expanded
   at validation into `areasPerRound` ordinary steps
   `<id>-area-1 … <id>-area-<P>` that run in parallel. Each round, reviewer
   `k` is given area `((round − 1) · P + (k − 1)) mod N` (round-robin), so
   every area is covered within `ceil(N / P)` rounds. The review's own id
   becomes the **group id**: the loop's `until.step` names it, and
   `dependsOn`, `blindTo` and `route.independentOf` that name it are
   rewritten to the reviewer ids. Retries, routing, blindTo, answer checking,
   resume and the dashboard need no new mechanism, because each reviewer is a
   step.
5. **Teaching.** SKILL.md lesson 6, program.md (Loop, condition form,
   Reviews), a new patterns.md pattern 6 "Fix until the review is dry", the
   plan contract, and two new validate advisories (a review loop that waits
   for `passed` with 3 or more rounds; a dry loop too short to cover its
   areas).

## 2. Why (benchmark 2026-10-10..12, as reported by the owner)

An Opus orchestrator built a stdlib SQL engine twice. Claude Code's ultracode
workflow won on quality with "loop until dry": parallel finders split by area,
a carried-forward list of known findings, a serial fixer, and a stop only when
a round finds nothing new. Bullswarm's best run used a loop `fix -> blind
review` with `until review.passed`, `maxRounds 4`: the reviews found 12, 22, 20
and 19 findings, never passed, and ran out of rounds. Every reviewer probed the
same angle (value semantics), none probed grammar, and 3 parser-precedence
bugs survived. Worker spend for the whole job was about 1.27M output tokens;
a fix round about 200k, a review about 40k.

Two things went wrong that the program could not express: "stop when nothing
new is found" (a strict review of a large change rarely says `passed: true`),
and "look from several angles each round" without the orchestrator hand-writing
and re-adding reviewers.

## 3. Feature 1: the dry stop

### 3.1 Syntax

```json
"loops": [
  { "id": "harden", "steps": ["review", "fix"], "until": { "step": "review", "dry": 1 }, "maxRounds": 4 }
]
```

`dry` is a whole number 1-3: how many rounds in a row must find nothing
fix-worthy. It is the third member of the one condition form:

| form | meaning | where |
|---|---|---|
| `{step, field, equals?}` | a boolean answer field | gate `when`, loop `until` (unchanged) |
| `{step, evidence: "passed"}` | every evidence check passed | gate `when`, loop `until` (unchanged) |
| `{step, dry: n}` | the review found nothing new for `n` rounds (and, with areas, every area was reviewed since the last finding) | loop `until` only |

Rejected alternatives: `{"step":"review","findings":"dry"}` cannot carry the
count; `dry: true` would be a second spelling of `dry: 1`. One spelling only.

### 3.2 The review's answer

The `until` step (or, with areas, the review step the areas belong to) must
declare an object answer whose required `findings` is an array of objects
whose required fields include `title` (string) and `inScope` (boolean). Two
optional item fields have a meaning to Bullswarm when declared:

- `stillOpen` (boolean): this repeats a known finding whose fix is missing or
  wrong. It counts as fix-worthy and keeps the loop going.
- `area` (string): ignored by the merge (Bullswarm knows each reviewer's
  area); allowed so a single reviewer can tag its findings.

Any other fields (`where`, `detail`, `repro`, `passed`, `checks`) are the
caller's and are passed through untouched. The minimal schema, printed by the
contract and by the validate issue:

```json
{ "type": "object", "required": ["findings"], "properties": { "findings": { "type": "array", "items": {
  "type": "object", "required": ["title", "inScope"],
  "properties": { "title": { "type": "string" }, "inScope": { "type": "boolean" }, "stillOpen": { "type": "boolean" },
                  "where": { "type": "string" }, "detail": { "type": "string" } } } } } }
```

Bullswarm does not add this schema on its own: the caller declares the answer,
as for every step (doctrine 6). The validate issue quotes it so an
orchestrator can paste it.

### 3.3 One round, step by step

Let `G` be the review group: the review step, or its area reviewers. Every
other loop step is a **fix step**. A fix step is **after** the review when it
depends on `G` (directly or through other loop steps), otherwise **before**.

1. Round `r` starts (round 1 when the loop's dependencies are done; later
   rounds through the existing kernel rerun, `rerunLoopBody`).
   - In round `r ≥ 2`, a *before* fix step is left out of the rerun request
     and marked skipped when round `r − 1` had no fix-worthy finding.
2. `G` runs. Each review prompt carries the review block (3.6).
3. When every step of `G` has succeeded, the kernel's control pass **merges**
   round `r` once (3.4) and records it on the loop's record, then in the same
   pass:
   - if the round had no fix-worthy finding, every *after* fix step of this
     round is settled `succeeded` with `skipped` (no worker runs);
   - if the dry verdict (3.5) holds, the loop passes with reason `dry`. No
     step of this round runs after it, and no round starts. A loop step that
     neither feeds the review nor follows it (a lint beside it) may still be
     running: the loop then passes when it succeeds, and is blocked if it
     fails, as any loop is. The merge does not wait for that step: a round
     is merged (and a clean round skips its fixer) even when the loop is
     already blocked by a failed step beside the review.
   - a reviewer that answers again after its round was merged (a `step
     rerun` of it) has the round merged again from the list as it stood
     before that round while the loop is pending, blocked or waiting; a
     waiting loop whose review has now run dry passes. A loop that passed
     dry learns the new answer too: still dry, it stays passed; not dry, it
     goes back to pending in that round and its fixer runs (implementation
     note 10).
4. Otherwise the remaining fix steps run. When every loop step has succeeded
   (or is skipped), the loop goes on exactly as today: out of rounds at
   `maxRounds` (waiting for the caller), else the next round.

Merge, skips and verdict are one state change, persisted together, so a kernel
that stops between them cannot run a fixer that should have been skipped.
The control pass already runs before the scheduler in every kernel iteration
(`v2-runtime.js`, `kernelControlPass` before `scheduleV2Actions`), so an
*after* fix step cannot be selected before the merge decides about it; the
fixer's prompt block (3.6) is built from state as well.

Recommended order is `[review, fix]` with the build outside the loop: round 1
reviews the build, and a clean build ends the loop after one review. The old
`[fix, review]` order also works (round 1's fix is then the writer, like
`draft` in patterns.md 3), and its later fix passes are skipped the same way.

### 3.4 Merging a round (dedup)

Input: the current checked answer of each step of `G` (`runtime.answer`,
set by `settleStepAnswer`), each with its area index (or none), and the
loop's known list. Output, all counts per round:

- `key(title)` = NFKC, trim, lower-case, collapse inner whitespace, drop one
  trailing `.`, on the whole title; titles are stored cut to 160 characters,
  a cut one with the 16-hex hash of its whole key (`key`), so two long titles
  that differ only past the cut stay two findings.
- A finding with a blank title is `ignored`.
- A finding whose key is not known and not yet seen this round is **new**
  (in scope or out of scope, as it says). It is added to the known list with
  `{title, round, area, inScope, from: <step id>}`.
- A finding whose key is already known (or seen earlier this round from
  another reviewer) is **repeated** unless it carries `stillOpen: true` and
  the known entry is in scope, in which case it is **reopened** (once per
  round; the round is added to the known entry's `reopened` list).
- A reviewer step with no answer (accepted by the caller after it failed) did
  not review its area this round.
- `fixWorthy(r) = new in-scope + reopened`.

The known list keeps at most 500 entries; past that, new titles are still
counted but not stored (`knownDropped`), and the prompt says so. 500 titles at
160 characters is about 80 KiB of state, well under the size of a run's
attempts list; the benchmark's 73 findings are about 6 KiB.

### 3.5 The dry verdict

With `lastFind` = the latest merged round with `fixWorthy > 0` (0 if none):

- `clean` = the number of merged rounds after `lastFind` in which at least
  one reviewer answered;
- `covered` = every area was reviewed (answered) in some round after
  `lastFind`; a review without areas has one implicit area;
- **dry** when `clean ≥ until.dry` and `covered`.

A round whose fixer ran is never the round that proves the fix: the next
review round does, because `lastFind` is the round that found it. That is the
ultracode rule ("stop when a round finds nothing new").

The verdict is a pure function of the record (`dryVerdict(loop, record)`), so
`readCondition` for the dry form, the watch, the Run page and the result all
read the same answer without storing it twice.

### 3.6 What each worker is told

`buildProgramWorkTask` (`step-prompts.js:140`) today appends
`previousRoundBlock` (`gates-loops.js:655`) to a loop step's prompt from
round 2. In a dry loop:

**A review step (or area reviewer), every round:**

```
## Review round (loop harden, round 2 of 4)
Focus on this area: grammar and parsing. Other reviewers cover expressions
and types, and joins and subqueries this round; report a finding outside
your area only when it is serious.
Write each problem as one finding:
- title: one short line naming what is wrong and where, under 160
  characters (a longer one is shown cut). Bullswarm tells new findings from
  known ones by the title, ignoring case, extra spaces and a final period, so
  reuse a known title word for word.
- inScope: true when the contract you were given requires it; false for style,
  wishes or anything it does not require (recorded, never fixed, does not
  keep the loop going).
- stillOpen: true only when you report a finding from the list below again
  because it is still present; use its exact title.
### Already known (report one again only if it is still present)
These were found in earlier rounds and handed to the fixer:
- [round 1 · grammar and parsing] Unary minus binds looser than ^ in expr.js
- [round 1 · joins and subqueries] LEFT JOIN drops rows with NULL keys
- (out of scope) [round 1] Error messages are not localised
Report findings that are not on this list. Report one on the list again only
when it is in scope and still present (its fix did not hold): use its exact
title and stillOpen: true. Leave out the rest of the list.
```

In a loop with no fix step the heading reads "(do not report again)" and the
last line "Report only findings that are not on this list."

The focus lines appear only with areas; the known section, and the stillOpen
line that points at it, only from round 2.
For the review group this block **replaces** `previousRoundBlock`: a reviewer
is never handed the fixer's answer or output, whether or not it is `blindTo`
the fixer. (It cannot be: `blindTo` may name only steps it depends on, and in
`[review, fix]` the review does not depend on the fix. Without this rule a
reviewer in round 2 would read the fixer's account, which is exactly what
`blindTo` exists to prevent.) The block names only facts Bullswarm keeps:
whether each fix step ran or was skipped last round, and its evidence status.

**A fix step, when it runs:**

```
## Findings to fix (loop harden, round 2 of 4)
The review found these in round 2 (3 new, 1 still open). Fix each one. If you
judge one is not a problem, leave it and say why in your report. The reviewers
do not read your report: one that still sees the problem reports it again as
still open, and the loop then runs another fix round, until its rounds run out
and the caller decides. This step passes only when it changes a file: if you
judge that none of them is a problem, change nothing and say why in your
report; the step then stops as "no file changed" and goes to the caller.
1. [grammar and parsing] Unary minus binds looser than ^ in expr.js
   {"title":"…","inScope":true,"where":"src/expr.js:88","detail":"…"}
2. …
Full answers: <answer file of each reviewer>
```

Each finding is printed as its full answer object, cut at 1,500 characters,
the block at 24,000 characters, with the answer files named for the rest.
Out-of-scope findings are not listed (only counted). This reuses the existing
way a loop step sees the previous round: the reviewers are the fix step's
dependencies, and `dependencyArtifacts` already hands it each reviewer's
answer file. The block adds the merged, de-duplicated list, read from the
attempts the round merged (its record names each reviewer's attempt in
`answers`, null for a reviewer with no answer that round), so a *before* fix
step never gets an older round's answer. A step of the loop that changes no
file (lane analyze) gets the same list headed "Review findings", for
reference, never told to fix it. `previousRoundBlock` for a fix step in a
dry loop keeps its own lines but leaves out the review group's answers (they
are in this block).

### 3.7 State

Loop record (`state.controlNodes[]`, `CONTROL_NODE_FIELDS` in
`v2-state.js:121`) gains one optional field, present only on a dry loop after
its first merge:

```json
"findings": {
  "rounds": [
    { "round": 1, "reviewed": [0, 1, 2], "new": 9, "reopened": 0, "repeated": 2, "outOfScope": 1, "ignored": 0, "fix": "runs" },
    { "round": 2, "reviewed": [3, 0, 1], "new": 0, "reopened": 0, "repeated": 4, "outOfScope": 0, "ignored": 0, "fix": "skipped" }
  ],
  "known": [ { "title": "Unary minus binds looser than ^ in expr.js", "round": 1, "area": 0, "inScope": true, "from": "review-area-1", "reopened": [] } ],
  "knownDropped": 0
}
```

`reviewed` holds area indexes (`[0]` for a review without areas, `[]` when no
reviewer answered). Each round also names the attempt each reviewer answered
in, `answers: {"review-area-1": "<attempt id>", "review-area-2": null}` (null:
no answer that round): the fixer's block reads exactly those answers, and a
reviewer whose current answer is another attempt (a `step rerun`) has the
round merged again. A known title stored cut carries `key`, the 16-hex hash of
its whole title, so the comparison stays whole. Record status `passed` with
`reason: "dry"` marks a dry stop. The validator checks the shape (integers, known areas within the
group's list, rounds ascending and not past `round`).

Step runtime (`state.actions[]`, `ACTION_STATE_FIELDS` in `v2-state.js:27`)
gains `skipped: {loopId, round, why, at}` on a fix step the loop skipped.
`status` is `succeeded` (its dependents inside the loop may proceed and the
run can complete), `outputFile` and the checked `answer` those of its last
succeeded run (none if it never ran), `attempts` unchanged. This follows the
existing precedent of `acceptance` (succeeded by the caller's choice, a marker
that every view words differently). Every reset clears it: `applyV2Revision`
(`v2-revision.js:470`) deletes `skipped` with `acceptance` and `answer` for
rerun, invalidated, amended and restored steps.

### 3.8 Events, watch, outcome, result

New and changed events (all through `appendEvent`; `controlWatchEvent` and
`renderControlEvent` in `gates-loops.js:562/594` pass them through):

| event | payload | watch line |
|---|---|---|
| `loop.findings` (new) | `{loopId, round, of, new, reopened, repeated, outOfScope, known, areas, unreviewed, clean, need, dry, fix}` | `· loop harden round 2 of 4 · review (grammar and parsing, expressions and types, joins and subqueries): 3 new, 1 still open, 4 repeated · 12 known · fix runs` |
| `action.finished` with `skipped` | `{actionId, status: "succeeded", skipped: {loopId, round, why}}` | `– fix skipped · loop harden round 3: nothing new to fix` |
| `loop.passed` | adds `reason: "dry"`, `known` | `✓ loop harden dry in round 3 of 4 · no new findings, every area reviewed · 12 found in all` |
| `loop.out-of-rounds` | adds `findings: {lastNew, known, unreviewed}` | `◷ loop harden out of rounds (4 of 4) · round 4 found 3 new (reviewed again: no) · not reviewed since: joins and subqueries · continue: …` |
| `loop.round` | unchanged | `↻ loop harden round 2 of 4 · review found 9 new` (wording from `describeCondition`) |

`loop.findings` is informational: `controlTrouble` and `isLoopVerdict` do not
wake on it. `watch --until trouble` still wakes only on `loop.out-of-rounds`,
failures and the end, and prints the `loop.passed` verdict line as today.

`describeCondition({step, dry})` → `review finds nothing new (1 round)`, with
areas `review finds nothing new (1 round, every area)`. `readCondition` for the
dry form finds the loop whose `until` it is and returns `dryVerdict(...).dry`,
or null before the first merge. A dry form is never a gate's `when`, so the
gate path never reads it.

Outcome: `loopOutcome` stays `passed` for a dry stop (the condition held), so
nothing that reads `outcome === 'passed'` changes. `loopOutcomes` adds
`findings: {known, outOfScope, rounds: [new per round], dryIn?, unreviewed?}`
to a dry loop's entry; `dryIn` is present only for a dry stop. The result
`reason` adds ` · loop harden ended dry in round 3 of 4 (12 findings)`.
`validateResultLoops` (`v2-outcome.js:1514`) accepts the optional `findings`.
`runs result --json` therefore carries the known titles; the full finding
objects stay in the reviewers' answers.

Proof line (`summaryProof`, `formatV2ProofLine`, `formatV2ProofLabel` in
`v2-outcome.js`): a skipped step is counted apart, never as proven, like an
acceptance: `proof: 2 steps proven (command 2) · 3 answer checked: … · 1
skipped (nothing to fix): fix`. The result action row gains optional
`skipped` (`exactFields` at `v2-outcome.js:203`).

Run page and dashboard (`v3-display.js` `loopFacts`): passed-dry row reads
`loop harden · dry in round 3 of 4 · 12 findings`; a pending dry loop between
rounds reads `round 3 of 4 · round 2: 0 new · not reviewed since: joins and
subqueries`. The skipped step row reads `skipped · nothing to fix (round 3)`.

### 3.10 Backward compatibility

- Programs, stored runs and results without `dry`/`areas` are byte-identical:
  no new field is written unless the dry form is used, and every new field is
  optional in the state and result validators.
- `field` and `evidence` loops keep "read the condition when the round is
  over" and never skip a step.
- A run that uses the new forms cannot be read by an older Bullswarm (its
  state validator refuses unknown fields); that is the existing rule for
  every additive state field.
- The schema version stays `bullswarm.workflow.program.v3`.

## 4. Feature 2: area reviewers that rotate

### 4.1 Syntax

On the review step:

```json
{ "id": "review", "dependsOn": ["build"], "blindTo": ["build"],
  "areas": ["grammar and parsing", "expressions and types", "joins and subqueries", "aggregates and ordering"],
  "areasPerRound": 3,
  "prompt": "…", "answer": { …findings schema… } }
```

- `areas`: 1 to 8 different one-line strings of at most 80 characters.
- `areasPerRound`: whole number from 1 to `min(N, 5)`; default `min(N, 3)`.
- Allowed only on a step that is the `until` step of a loop whose `until` is
  the dry form, with lane `analyze` and no `outward` deliverable (its
  reviewers run side by side and must not write files).

### 4.2 Decision: reviewers are real steps, a fixed set of `P`, the area rotates

Options considered:

| option | cost |
|---|---|
| Parallel **attempts** of one step | The attempt model is serial per step: `activeTasks` is keyed by step id, `currentAttemptId`, `runtime.status`, `retriesAlready`/`refusalsAlready` count per step, `supersededAttempts` is one floor, `settleStepAnswer` keeps one answer, files are `task-<step>-attempt-<n>.md`. Parallel attempts touch the core dispatch path. Rejected. |
| One step **per area** (`N` steps), `N − P` skipped each round | Area per step is fixed, nice for display, but unselected reviewers must be skipped at the start of every round including round 1, before the scheduler can pick them: a new timing hazard. Rejected for this release. |
| **`P` reviewer steps, area chosen per round** | Every reviewer runs every round, which is what loops already do; the area is a pure function of (reviewer, round) read when the prompt is built. Chosen. |

Ids: `<id>-area-1 … <id>-area-<P>`. `@` (as in `review@grammar`) is refused by
the id rule in `program-v3.js` (`ID_RE`), `v2-scheduler.js` and the state
validator, and ends up in file names and CLI arguments. The reviewer ids are
claimed in the shared id space, so a collision is the existing "id is used
twice" issue, worded: `id "review-area-2" is used twice; steps, gates and loops share one id space (review's areas use review-area-1 to review-area-3)`.

Area of reviewer `k` (1-based) in round `r`: index `((r − 1) · P + (k − 1)) mod N`.
With `P = N` there is no rotation. With N=4, P=3: round 1 → 0,1,2; round 2 →
3,0,1; round 3 → 2,3,0. A retry or resume in the same round gets the same area.

Labels (derived, stored): with `P = N`, `<label or id> · <area>`; with
rotation, `<label or id> · area reviewer k of P` (the Run page shows each
attempt's area, derived from `attemptRounds` in `v3-display.js:161`).

### 4.3 Expansion (normalisation)

A pre-pass `expandAreas(program)` runs in `normaliseProgramV3` right after
`authoredShape`, before any other check:

- A step with `areas` and no `areaOf` is replaced, in place, by `P` copies.
  Each copy has the review's fields (prompt, lane, effort, reasoning, model,
  timeBox, retry, route, blindTo, answer, evidence, phase, dependsOn), its own
  id and label, and a derived `areaOf: {step: "review", slot: k, areas: [...]}`.
  `areas` and `areasPerRound` are not stored on the copies (P is the number
  of copies).
- Every `dependsOn`, `blindTo`, `route.independentOf` and loop `steps` entry
  naming the review id is replaced by the reviewer ids, in order.
- The loop's `until` keeps `{step: "review", dry: n}`: the review id is the
  group id, claimed in the id space as kind `group`.
- A step that already has `areaOf` (a stored program, or `workflow add`
  re-validating a run's own steps) is not expanded again. The group is
  checked instead: slots `1..P` all present, same `areas`, every field equal
  except `id`, `label` and `areaOf.slot`. So the stored form normalises to
  itself (the property `revision-v3.js` depends on).
- `areaOf` joins `DERIVED_KEYS` (accepted on input only with the derived
  value).
- Issue wording maps an expanded index back to the authored one:
  `steps[3] (review, area reviewer 2)`.

Rules on the group id: a gate `when` on it is refused (`review is a group of area reviewers; only a loop's until may name it, in the dry form`);
a step outside the loop that depends on it gets the existing message,
worded with the group (`… depends on review inside loop harden; depend on the loop harden instead`).

### 4.4 How the kernel treats reviewers

Because each reviewer is a step, these work unchanged:

- **Parallelism**: the scheduler runs every ready step; reviewers are
  analyze, own no files, so they run side by side up to the run's
  `concurrency`.
- **Routing**: each reviewer is picked by pace like any step; `route` is
  copied, so `independentOf`/`providers`/`pools` apply to each. Bullswarm does
  not spread reviewers over pools on its own (doctrine 6).
- **Retries**: each reviewer has its own one retry and refusal re-picks.
- **Answer checking**: each reviewer's answer is checked against the same
  schema; a mismatch is failure kind `schema` with the same-pool correction.
- **blindTo**: copied; the fixer's account never reaches a reviewer (3.6).
  Reviewers of one round cannot see each other (they run at the same time and
  do not depend on each other).
- **Failure**: a reviewer that fails after its retry blocks the loop, as any
  loop step does today; the caller reruns it (same area) or accepts it (its
  area counts as not reviewed this round, so the dry verdict cannot pass on
  it).
- **Dashboard**: reviewers are ordinary rows in the review's phase.

Merge (3.4) reads all reviewers' answers once all have succeeded; findings
seen by two reviewers in a round count once. Dry with areas is 3.5 with
`covered`: no new fix-worthy finding *and* every area answered in a round
after the last finding. So rotation cannot stop on an unvisited area.

### 4.5 CLI verbs on the group id

- `workflow wait <run> review`: waits for all reviewers and prints each
  answer (the wait reader resolves a group id to its reviewers).
- `workflow step rerun|accept <run> review`: refused with
  `review is a group of area reviewers (review-area-1 to review-area-3); name one of them`.
- `workflow wait <run> harden`: the loop line includes its findings summary.

## 5. Economy (stated in the skill)

Using the benchmark's figures (about 40k output tokens per review, about 200k
per fix round; real cost depends on the size of the work):

- a round that finds something: `P × 40k + 200k`;
- a clean round: `P × 40k` (the fixer is skipped);
- worst case for a loop: `maxRounds × P × 40k + maxRounds × 200k`.

| shape | worst case | note |
|---|---|---|
| benchmark loop: 1 reviewer, 4 rounds, all finding | 4 × 40k + 4 × 200k = 960k | what ran |
| 3 areas, all every round, 3 rounds | 3 × 120k + 3 × 200k = 960k | same ceiling, three angles every round |
| 4 areas, 3 per round, 4 rounds | 4 × 120k + 4 × 200k = 1.28M | full coverage needs 2 clean rounds after a finding |
| 3 areas, all every round, 4 rounds | 1.28M | only if every round finds something |

The dry stop saves the rounds after the review runs out of new findings; the
area reviewers cost about `(P − 1) × 40k` more per round than one review.
Recommendation in the skill: 3 areas reviewed every round (`P = N = 3`) and
`maxRounds` 3 or 4; more areas only when the contract is broad, knowing they
rotate.

## 10. Edge cases

| case | behaviour |
|---|---|
| A reviewer fails (after its retry) | Loop blocked, as any failed loop step. Caller: `step rerun review-area-2` (same area, same round) or `step accept` (area not reviewed this round; the dry verdict cannot pass on it). The other reviewers' answers are kept; the merge waits for the group. |
| A reviewer's answer is malformed | Failure kind `schema`, same-pool correction retry, then the caller. Valid but odd answers: duplicate titles in one answer count once; blank titles are ignored and counted; a reworded known finding counts as new (the prompt asks for exact titles; maxRounds bounds the cost). |
| `maxRounds` reached | Same as today: the loop waits out of rounds. The note says what the last round found and which areas were not reviewed since; if the last round's fixer ran, its fix was not reviewed. `continue --rounds n` keeps the record; `continue` alone ends it continued-unmet, never dry. |
| `areas` with 1 entry | One reviewer `review-area-1` with a focus line; advisory `review-one-area`. |
| `areasPerRound` equal to N | No rotation; each reviewer keeps its area. |
| Resuming a run | Everything is in state: the round, the merged rounds, the known list, the skip markers. The area is a pure function of (reviewer, round). The merge is keyed by round and done once, in the same state change as the skips and the verdict. |
| `workflow add` into a loop | Unchanged rule: a fragment cannot add steps to an existing loop, and `blocks` cannot name a loop step (reviewers included). A fragment may add a new dry loop with areas; it is expanded with the rest of the request. A fragment step depending on a group id gets "depend on the loop instead". |
| A fixer judges every finding wrong and changes nothing | Its `files` deliverable fails `not-produced` as today, and comes to the caller after its retry; the caller accepts it. The Findings block says a rejected finding must be explained in the report. |
| The fixer leaves a finding unfixed | Not re-reported as new (it is known), but a reviewer that sees it still present reports it with `stillOpen: true`, which keeps the loop going and reaches the fixer again. |
| A step reruns after its loop passed | A field or evidence loop: existing behaviour. A loop that passed dry merges its review's new answer (implementation note 10). |
| A dry loop whose only step is the review | Allowed: "find until dry", collecting known findings for a later fix step that depends on the loop. |
| Steps after the review that depend on the fixer (`[review, fix, test]`) | All are fix steps; all are skipped together on a clean round. |
| Concurrency 1 | Reviewers run one after the other; nothing else changes. |
| Old Bullswarm reads a new run | Refused by its state validator (unknown field), as for every additive field. |

## Implementation notes

Implemented 2026-10-14 on `v0.38.12/ultracode-lessons`. Where the code showed
part of the design to be wrong or under-specified, the safest working variant
was taken:

1. **A skipped "before" step is rerun, then settled skipped.** Section 3.3
   says a *before* fix step is "left out of the rerun request". Leaving it out
   keeps its previous round's `succeeded` runtime, output file and attempt
   floor, so `previousRoundBlock` and the fixer block would read the wrong
   round. The loop's rerun request still names every loop step; in the same
   control pass (one state change, before any event) each *before* step is
   settled `succeeded` with `skipped`. Observable behaviour is the design's.
   The round number and these skips are applied inside the rerun, before its
   `program.revised` event saves the state, so a kernel stopped right after
   that save resumes with the skip in place.
2. **A skipped step's phase starts and completes.** A step settled without a
   worker never started its presentation stage, and the next revision
   (`workflow add`) then stored a stage completed before it started, which the
   state validator refuses. The control pass now starts and completes the
   skipped step's phase as the kernel does for a step it blocks
   (`emitSkipped` in `gates-loops.js`, using `v2-presentation.js` helpers).
3. **Issue wording keeps the authored index.** An issue about an area reviewer
   reads `steps[1] …` (the review's own index), without the
   "(review, area reviewer 2)" suffix of section 4.3, so a problem every copy
   shares is reported once. v2-rule issues (`actions[i]`) are mapped back to
   the authored index too. `fragmentWording` in `revision-v3.js` needed no
   change: a stored program's reviewers map 1:1 to their input index.
4. **The group-id refusal for `step rerun|accept`** lives where those verbs
   load the run (`loadStepRun` in `cli-step-verbs.js`), not in
   `v2-revision.js`; the message is the design's.
5. **Pattern 6 and the contract example use exact files and a pytest check.**
   The design's `"files": ["src/query/"]` is a directory, which the validator
   refuses. The example names `src/query/engine.py` and
   `tests/test_engine.py`, and uses `maxRounds` 3 (the 960k ceiling section 5
   recommends) instead of 4. The contract prints it as `dryLoopExample`, and
   the docs test keeps it equal to patterns.md 6.
6. **Shapes the design left open.** `loops[i].findings` in the result is
   `{known: [in-scope titles], outOfScope: [titles], rounds: [new in-scope per
   round], dryIn?, unreviewed?: [area names]}`. A round's `fix` is `runs`,
   `skipped`, or `none` (a loop whose only step is the review). A known
   finding's `area` is `0` for a review without areas. `loop.round` of a dry
   loop carries `found: {new, reopened}` so the watch line reads
   `the review found 9 new`. The review block says whether the fix ran last
   round (from the loop record), not its evidence status.
7. **Advisories.** `dry-loop-too-short` also fires for a dry loop without
   areas whose `maxRounds` leaves no room for `dry` clean rounds after a
   finding. A fourth code was added at the owner's request:
   `compile-check-only` (a step whose every command check only compiles or
   parses the files, such as `python -m py_compile`, `node --check`, `tsc
   --noEmit`, `cargo check`). `PROGRAM_ADVISORY_CODES` now lists eight codes (nine with
   `dry-loop-fix-first`, note 9).
8. **Not done in this release.** The Run page does not yet show each
   reviewer attempt's area (section 4.2's attempt area fact); the step row
   says `skipped · nothing to fix (round n)`. The public guides
   (`docs/guide/workflows.md`, `docs/reference/program.md`) are unchanged; the
   skill, the contract and the help text teach the new forms.
9. **After review (2026-10-14).**
   - A reviewer is blind to the loop's fix steps it depends on (`[fix,
     review]`), so 3.6's "never handed the fixer's answer or output, blindTo
     or not" holds in both orders; a fix step `blindTo` the review gets a
     one-line block instead of the findings.
   - A loop whose only step is the review does not ask for `stillOpen` and
     reads it as a repeat: nothing fixes a known finding between rounds.
   - Within one round, a title one reviewer marks in scope is in scope,
     whatever the order the reviewers answered in.
   - Past the 500-title cap a title is kept as a 16-hex hash of its key
     (`findings.dropped`, at most 5,000), so a later round counts it as a
     repeat and `knownDropped` counts it once.
   - A step that depends on some but not all of a group's reviewers is
     refused; it would start before the round is merged.
   - With a fix step in the loop, a findings schema whose items allow no
     other field must list `stillOpen`.
   - Areas that differ only in case or spacing are one area twice.
   - A fix step that ran in an earlier round and is then skipped keeps that
     run's output file and proof; only a step that never ran is counted as
     `skipped` in the proof line.
   - The fixer's Previous round block says a fix step was skipped last round
     instead of showing an older attempt; a fix step before the review is
     told in round 1 that no review has run yet; advisory
     `dry-loop-fix-first` names a `[fix, review]` loop on work built outside
     it.
10. **Second review (2026-10-14).**
   - A **fixer** is a fix step that can change files (lane `build` or
     `chore`). Only fixers count where a fix is meant: a reviewer is blinded
     only to the fixers it depends on (a test run it depends on is handed to
     it); a loop with no fixer ("find until dry" beside a lint) asks no
     `stillOpen`, reads it as a repeat, and its watch and waiting note name
     no fix; `dry-loop-fix-first` fires only on a fixer, and its advice keeps
     every loop step. Skips still apply to every fix step, as in 3.3.
   - The review block lists only findings of rounds before the current one
     (`knownBefore`), so a reviewer rerun in its round is not told that
     round's own findings were known; out-of-scope findings are listed under
     their own heading, never as handed to the fixer.
   - A loop that passed dry is no longer final for its own review: a
     reviewer that answers again (its own rerun, or a rerun of the work it
     reviews) has the round merged again. Still dry, the loop stays passed
     and a fixer that reran is skipped; not dry, the loop goes back to
     pending in that round, the fixer runs with the findings, and the loop
     goes on (the steps after it rerun with its next round). Before, the
     fixer ran with no findings and the finding was dropped from the record.
   - Every title is found by the hash of its whole key, so a long title that
     differs from another only by a final period is the same finding.
   - `loops[i].findings.stillOpen` (per round, present once a round reported
     one) and the `workflow wait` findings line count known findings
     reported still open.
11. **Third review (2026-10-14).**
   - A loop the caller ended with `workflow continue` learns a reviewer's new
     answer like one that passed dry (`passed` with reason `continued`): the
     round is merged again, the finding reaches the fixer, and the loop goes
     back to pending in that round (out of rounds, it waits again).
   - `onceFixersOf`: a fixer before the review in a loop that also has a fixer
     after it (`[build, review, fix]`) runs in round 1 only and is skipped from
     round 2 (`skipped.why` says its work was done in round 1). The fixer
     after the review is the only step handed the findings, and the reviewer's
     "went to ..." line names only it. A read-only step before the review (a
     test run) is not one and reruns after each fix.
   - The default `claude-code` pool is spawned with `--strict-mcp-config`
     (provider.mjs `connectors`): without `CLAUDE_CONFIG_DIR` `claude` reads
     `~/.claude.json`, whose user-scope MCP servers (on the author's machine
     railway and whatsapp, connected without auth) a worker run with
     `--dangerously-skip-permissions` would start. Named homes keep their spawn.
     The flag ignores every MCP configuration but `--mcp-config` (never passed),
     so a default-pool worker has no MCP server at all: the plugin servers in
     `enabledPlugins` and the claude.ai connectors that a 0.38.11 worker under
     `~/.claude` still loaded are gone from it too (checked with `claude`
     2.1.299: the init message lists no `plugin:posthog` server with the flag,
     and lists it without). A step that needs a connector routes to a named
     home (`route.pools.use`).
   - Not changed: a named home whose access token has lapsed is not discovered
     as a pool (`connectors` reads usable tokens only), as on 0.38.11; only the
     default pool, which always exists, reads `expired` rather than `no_token`.
   - Watch: for a step whose progress is output, a late or `--since` watcher
     takes the level at its last output as 1 (a step that prints is not silent
     between lines), so it prints the level an all-along watcher shows and never
     skips one; for file-change progress the earlier rule stands.
12. **Fourth review (2026-10-14).**
   - A dry loop reopened from `passed` (dry or continued) resets the finished
     steps that depend on the loop in the same pass (`rerunStepsBehind`, one
     kernel revision), because at its last round no `nextRound` rerun reaches
     them; they cannot start before the loop ends again.
   - "Behind" is every step that depends on the loop directly or through a
     gate or a later loop (`stepsBehind`); a gate the caller had passed goes
     back to `pending` in the same change (event `gate.reopened`), so it waits
     for the new result and the approval of the old one does not stand.
   - A step behind the loop that is still running holds the reopen back: the
     new answer stays unmerged (`mergeDryRound` returns false before it changes
     anything) and is merged when that step has finished, which then reruns it.
     A running step cannot be reset by the kernel's own rerun, and leaving it
     running behind a pending loop broke the scheduler's rule that an active
     step has no unfinished dependency.
   - The loop record keeps `accepted` (step id to the acceptance), snapshotted
     by `nextRound` before its rerun erases it; `skipSteps` puts it back on a
     step it skips only when no attempt has run since the one accepted. The
     result then reads the step as accepted by choice, never as skipped.
   - `workflow wait` carries `skipped` and `acceptance` per step, and a step
     with either and no succeeded attempt has `deliverable.produced: null`.
   - A failed edit is not a file change (`lastFileChange` in stale.js): an edit
     in flight counts from its start, a finished one from its start, a failed
     one not at all, and it restores the command repeat it interrupted.
   - MCP: see note 11; `--strict-mcp-config` also removes plugin and
     claude.ai connector servers from the default pool's workers.
