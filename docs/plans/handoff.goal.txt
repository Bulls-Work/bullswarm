Attempt handoff in /Users/cowcow02/Repo/bullswork/bullswarm-handoff: when one worker dies mid-flight (stall, provider error, empty or thin answer, crash) and the same step is re-dispatched, the next worker — on any pool, any vendor CLI — starts from what the previous one left, not cold. Everything handed over is deterministic, built from files the kernel already holds; no model summarises another model's work. Free models that die mid-flight are the motivating case.

1. Every attempt's normalized event stream is persisted: the kernel appends each event the connector's `eventStream` adapter decodes (src/lib/agent-events.js) to `stream-<actionId>-attempt-<N>.jsonl` in the run directory, one JSON object per line with `seq`, `at` (ISO, kernel-stamped), `source`, `providerType`, `kind`, `status`, `summary`; the file is bounded (a head and a tail with one `{"truncated":true,"dropped":<n>}` marker line between them when the cap is hit) and a connector with no `eventStream` gets a bounded plain `stdout-<actionId>-attempt-<N>.log` tail instead; the attempt record carries `streamFile`.
2. `response` events keep their full text in the persisted stream, bounded per event, while the live pane keeps today's compact summary; the caps are core defaults that a connector manifest may override in an optional `eventStream.capture` block declared in src/providers/_schema.json and accepted by `bullswarm providers validate`, so a contributed connector needs no code to take part.
3. When attempt N of a step ends without success and the dispatcher starts attempt N+1 of the same step (cross-pool fallback or same-pool mechanical retry, not the schema-correction path that already appends its own block), the task text handed to attempt N+1 ends with a `## Prior attempt on this step` block that is a fixed template filled from on-disk facts: pool, model, start, end, duration, failure kind and `why`; the files attempt N changed inside the step's territory as a `git diff --stat` taken at the moment attempt N ended (never later, so sibling edits made afterwards are not attributed to it); the path and byte count of its final answer or partial output; its last three `response` events with timestamps; the path of its stream file; and the sentence that the edits are unverified and the new worker decides whether to keep, fix or revert them and must report which. The log is referenced by path, never inlined.
4. The attempt record and the `attempt.finished` event record `outputFile` and its byte count whenever the file exists, including on failure (today a failed attempt records `outputFile: null` although the file is on disk), plus `handoff: { from: <attemptId>, bytes }` on the receiving attempt; `bullswarm workflow action show <run> <step>` prints `streamFile`, the diff snapshot path and the handoff, and `bullswarm workflow watch` prints one line at the handoff naming the file count and the last response.
5. Tests under tests/ cover: the persisted stream (shape, `at`, cap and marker, no-eventStream fallback) for the codex, claude-code, command-code and opencode2 line shapes already used in tests/agent-events.test.js; the manifest `capture` block accepted and applied; the handoff block asserted as a string against a fixture run with tests/fixtures/stalling-connector.mjs and tests/fixtures/answering-connector.mjs where attempt 2's task file names attempt 1's edits, partial output and last responses; the state schema round-trip for every new attempt field; and `npm test` passes.
6. docs/guide/workflows.md (or observing.md, whichever already describes attempts) explains the stream file and the handoff block with a real excerpt from a fixture run; the connector authoring notes beside src/providers/_schema.json describe `eventStream.capture`; CHANGELOG.md `## Unreleased` carries the entry; package.json is not bumped.
